## 二、【待修·已向用户汇报】「新建事件」确认按钮点了没反应

**根因**：`show_yourwindows.py:3104`
```python
self.events[month+day] = {'things': text}   # self.events 是 list！
```
第 49 行 `self.events = []` 初始化为 **list**，全项目 12 处（2168/2351/2577/2617/
2709/2828-2830/3347/3375）都按 list-of-dict 用 `for event in self.events: event['month']`。
用字符串下标赋值 list → `TypeError: list indices must be integers or slices, not str`。

**为什么表现成"按钮点不动"**：异常抛在 ttk.Button 的 command 回调里，Tkinter 交给
默认 `report_callback_exception` → 只打印到 stderr；打包后 `console=False`，所以
完全静默。异常发生在 `messagebox.showinfo("成功",...)` **之前**，连成功弹窗都没有。

**引入点**：3098-3102 行**原本正确的 `self.events.append({...})` 被注释掉了**，
换成了 3104 的 dict 写法。

**次要隐患**：导入时 month/day 补零成 `"09"`/`"26"`（字符串），而新建时用户输入
`"1"` 不补零 → 3170-3173 的预填比较 `event['month'] == month_choice` 会失配。

**修复方向**（待用户确认后做）：恢复 append 语义 + 按注释意图实现"同日期覆盖"，
把 month/day 统一成两位字符串；建议给 Tk 装 `report_callback_exception` 兜底，
让回调异常弹窗可见，避免今后同类 bug 继续表现为"按钮点不动"。

**用户要求**：修复后的最终交付物 = 含完整 EXE 的 ZIP 压缩包。

## 三、【重大纠正】打包环境与源码 Qt 绑定不匹配 —— 之前打出的包全是废包

**这是本次最重要的发现，推翻了第一、二节的假设。**

### 3.1 三个 exe 的解剖结果（用 PyInstaller CArchiveReader 读 TOC）

| 文件 | 时间 | python | Qt | 判定 |
|---|---|---|---|---|
| `dist/日程表_Win7.exe` | 09-27 12:21 | python38.dll | **无** | 废包 |
| `win7_dist/日程表_Win7.exe` | 10-01 18:18 | python38.dll | 无（PySide6 missing） | 废包 |
| `../ScheduleMate_Win7/日程表_Win7.exe` | 09-30 20:47 | python38.dll | **Qt5Core + PySide2×120** | **能用（用户实际在跑的就是它）** |

`build/日程表/Analysis-00.toc`（09-27 07:46）里有 319 条 PySide6，但那次的产物是
onedir 的 `dist/codingzhou-日程表/`，与 `dist/日程表_Win7.exe` 不是同一批。

### 3.2 两个 Python 环境的真实分工

- **`D:\python.exe`**：Python 3.12.1 + **PySide6 6.11.0** + PyInstaller 6.10.0 + pandas 3.0.1
  → 对应源码（`show_yourwindows.py` 里 `from PySide6...`）。**但 Python 3.12/Qt6 都不支持 Win7。**
- **`C:\py38\python.exe`**：Python 3.8.10 + **PySide2 5.15.2** + PyInstaller 5.13.2
  → 唯一能出「Win7 可运行」exe 的环境（Python 3.8 是最后支持 Win7 的版本，Qt5 也支持）。

**问题**：源码是 PySide6，却拿 PySide2 环境打包 → PyInstaller 只把 PySide6 记进
`warn-*.txt` 的 *missing module*，**exit=0 照样成功**，产出启动即 `ModuleNotFoundError` 的包。
10-01 那次"重打包成功"就是这么来的。**教训：PyInstaller exit=0 不等于包能用，
必须验证 TOC 里 Qt 绑定是否齐全。**

### 3.3 用户实际运行的包 = PySide2 版

`ScheduleMate_Win7/日程表_Win7.exe` 内嵌主脚本里 **PySide6 出现 0 次、PySide2 出现 3 次**，
说明历史上曾把源码适配成 PySide2 后打过一次（但那份源码没留在工作区，只存在于 exe 里）。

### 3.4 解决：双绑定兼容层

既然「Win7 必须能跑」是硬需求，而 API 差异只有 2 处，就在源码里做兼容：

```python
try:
    from PySide6.QtWidgets import ...
    QT_BINDING = "PySide6"
except ImportError:
    from PySide2.QtWidgets import ...
    QT_BINDING = "PySide2"
```

Qt6/Qt5 差异点（全项目仅 3 处，已用辅助函数抹平）：
- `event.globalPosition().toPoint()`（Qt6）↔ `event.globalPos()`（Qt5）→ `_global_pos(event)`，6 处
- `QMenu.exec()` ↔ `QMenu.exec_()` → `_exec_menu(menu, pos)`，2 处
- `app.exec()` ↔ `app.exec_()` → `getattr(app, "exec", None) or app.exec_`，1 处

### 3.5 又一个坑：Tk 8.6.9 / 8.6.12 版本冲突

第一次重打包后的 exe，主窗口正常，但**点开日历就崩**：
```
_tkinter.TclError: version conflict for package "Tk": have 8.6.9, need exactly 8.6.12
```
根因：第一节那次"修 Tcl/Tk"从 `D:\Python39` 拷来的是 **Tk 8.6.12 脚本**，
而 `C:\py38` 的 Tcl 运行时是 **8.6.9**（`tcl8.6/init.tcl` 里 `package require -exact Tcl 8.6.9`）。

**取证**：对比两个包内嵌的 `tk\tk.tcl` —— 能用的那个要求 **Tk 8.6.9**，我打的包要求 **8.6.12**。

**修复**：从用户可用的 `ScheduleMate_Win7\日程表_Win7.exe` 里用 CArchiveReader
**提取 87 个 tk 数据文件**，覆盖回 `C:\py38\tcl\tk8.6\`（原 8.6.12 目录重命名为
`tk8.6.bak-8.6.12` 备份）。验证：`Tcl/Tk/Ttk 全部 8.6.9`，`ttk.Scale`/`ttk.Checkbutton` 正常。

（附带无害告警：`dde1.4`、`reg1.3` 的 `pkgIndex.tcl` 报 `unknown encoding "cp1252"`，
是 tcl 的 encoding 目录缺 cp1252，程序不用这两个包，忽略。）

## 四、三个 bug 的确认结论与修复

### 4.1 「新建事件」确认按钮点不动 —— 确认存在，已修

见第二节。修复：把 `self.events[month+day] = {...}` 改成「同日期覆盖、否则追加」：
```python
self.events = [e for e in self.events
               if not (isinstance(e, dict)
                       and _norm(e.get('month')) == _m
                       and _norm(e.get('day')) == _d)]
self.events.append({'month': "%02d" % _m, 'day': "%02d" % _d, 'things': text})
```
并把「新建事件」的预填比较改成数值比较（修掉 `"09"` vs `"9"` 失配）。

**另外补了兜底**：新增 `ensure_tk_error_hook()`，接管
`tk._default_root.report_callback_exception`，把回调异常弹窗 + 写 `error.log`。
以后同类问题不会再表现成"按钮点不动"。已在 4 处 Toplevel/Tk 创建后调用。

### 4.2 两个透明度 —— 结论是「功能缺失」，不是「坏掉」

grep 确认修改前**整个项目没有任何** `setWindowOpacity` / `QGraphicsOpacityEffect` 代码，
设置界面里也没有相关控件。所以不是 bug，是从未实现。

**已实现**（按用户澄清的对象）：
- **桌面图标透明度** = 主窗口整体（今天是什么 + 今日事件 + 日历图标那张图）
  → `self.setWindowOpacity(v)`，滑块 20%–100%
- **最小化图标透明度** = 主窗口里那张大图
  → `QGraphicsOpacityEffect` 挂在 `self.image_label`，滑块 0%–100%

### 4.3 设置持久化 + 一个隐藏坑

`user_data.json` 新增 `window_opacity` / `icon_opacity`，用
`load_user_settings()` / `save_user_settings()` 读写（保留 `user_data` 等其它键，
文件损坏时回落默认值不崩）。

**坑**：Qt 的 `app.exec()` 是主循环，Tk 的 `cal_window.mainloop()` 是**嵌套**在 Qt 回调里跑的
（打开日历窗口时）。嵌套期间 Qt 事件循环被完全阻塞，所以从 Tk 回调里调用
`setWindowOpacity` 后窗口不会立刻重绘，用户会以为"拖了滑块没反应"。
→ 新增 `_pump_qt_events()`，在透明度回调里手动 `processEvents()` 泵一次。

**另一个坑**：`ttk.Scale.get()` 返回 float，而 Qt 的 `setMaximumHeight()` 只收 int
（原来的"事件框长度"滑块有崩的风险）→ 已加 `int(round(float(...)))`。

## 八、【已确认·待修复】「桌面图标透明度」不是真的透明，而是整体变淡

**用户反馈**：调小透明度感觉是「调暗了」而不是透明；期望像手机相机那样
「把底色去掉、内容嵌在桌面中间」。**这个观察是对的，问题确实存在。**

### 根因

`setWindowOpacity()` 是 Qt 的「**整个窗口统一 alpha**」，
把**文字和底色一起**按比例稀释，而不是「只让底色消失」。

而窗口里两个文字框各自带着很实的底色：
- `content_label`（今日事件）：`rgba(255,255,255,0.9)` 白 90%
- `countdown_label`（倒计时）：`rgba(64,158,255,0.8)` 蓝 80%
- `image_label`：`rgba(255,255,255,0.1)`

窗口本身是透明的（`WA_TranslucentBackground`），挡住视线的是**这两个框的底色**。

### 实测（probe_opacity.py，追踪同一批文字像素；文字本色 #333333 = 灰度 51）

| 设置 | 文字灰度 | 偏离本色 | 底色灰度 |
|---|---|---|---|
| window_opacity 1.00 | 64.7 | 13.7 | 253.0 |
| window_opacity 0.60 | 134.5 | 83.5 | 248.0 |
| window_opacity 0.30 | **186.4** | **135.4** | 244.6 |
| **只降底色 alpha 到 0.15** | **63.9** | 12.9 | 242.2 |

文字被稀释了近 3 倍（64.7 → 186.4），底色几乎没变。

### 为什么观感是「变暗」

用户桌面是**浅色**，白框变透明后与桌面几乎同色 → 看不出「消失」；
唯一明显变化的是文字变淡 → 综合观感就成了「调暗」。
（用抓屏像素反推：0.30 时文字 0.3×51 + 0.7×255 ≈ 193，与实测 186 吻合。）

### 修复方向（待用户确认后实施）

把「桌面图标透明度」从「整体窗口 alpha」改成「**底色 alpha**」：
只调 `content_label` / `countdown_label` 底色的 alpha，
文字与图标保持不透明 → 才是「底色去掉、内容嵌进桌面」。

注意：若用户桌面是深色，深灰文字在透明底色上会看不清，
可能需要顺带给文字加描边/阴影，或让文字色也可调。

**对比**：`icon_opacity`（最小化图标透明度）用的是 `QGraphicsOpacityEffect`
挂在 `image_label` 上，只影响那一张图、不影响文字 —— 那个实现是**正确**的。

### 已按用户要求修复（文字不随透明度变化）

新增 `MyWindow.apply_window_opacity(value=None)`：
- `self.setWindowOpacity(1.0)` —— 窗口本身**恒不透明**，这是关键，否则文字会被整体 alpha 稀释
- 只改各控件底色的 alpha：`content_label` 0.9×f、`countdown_label` 0.8×f、`image_label` 0.1×f
- 倒计时是**白字**，底色淡下去在浅色桌面会看不见 → alpha < 0.45 时字色自动切
  `#FFFFFF` → `#14487a`（始终是不透明实色，只是换色以适应背景）
- 滑块范围 20~100 改为 **0~100**，允许底色完全消失
- **坑**：Windows 下 alpha=0 的区域会「点击穿透」，窗口就拖不动了 →
  给 `central_widget` 铺一层 `rgba(255,255,255,0.01)` 的看不见底座，视觉无感但能接收鼠标

设置界面标签改为「桌面图标透明度（底色）」，提示这是调底色不是调亮度。

### 修复后实测（probe_opacity.py，追踪同一批文字像素，本色灰度 51）

| 设置 | 文字灰度 | 偏离本色 | 底色灰度 |
|---|---|---|---|
| 透明度 1.00 | 64.1 | 13.1 | 245.9 |
| 透明度 0.30 | 59.7 | 8.7 | 192.8 |
| 透明度 0.00 | **57.9** | **6.9** | 170.3 |
| *旧实现 0.30* | *126.7* | **75.7** | — |

文字几乎不动，底色一路降到露出桌面内容。**修复成立。**

## 九、【已确认+已修】「设置改了保存不了」的真正原因

用户反馈「设置里面改了以后保存不了」。**值其实存进去了**，是**启动时没读**。

**连带 bug**：`self.event_length` 在 `__init__` 里**从未初始化**

- `initUI` 改为 `setMaximumHeight(int(round(float(self.event_length))))`
- `DEFAULT_USER_SETTINGS['event_length']` 200 → **560**（与原来写死值一致，
  保证首次使用观感不变；若不改，新用户会突然发现窗口矮了 360px）
- 设置界面滑块初值 200 → 560

**其余设置项启动时均已正确应用**（window_opacity / icon_opacity / text_size / autostart），
所以「保存不了」只有「事件框长度」这一项。

## 十二、「改字号像调分辨率」的根治（本轮核心）

用户反馈：「现在这样一调，就把那个显示框全部调整了。它应该不是调字体的大小，是调那个分辨率了。」

### 根因（两个，缺一不可）
1. **Qt sizeHint 连锁**：改字号 → QTextEdit/QLabel 的 sizeHint 变大 → 布局把白框和窗口一起撑大。
2. **每秒刷新的倒计时**：`update_content()` 每秒调一次 `_fit_content_height()`，
   把 `apply_text_size()` 刚锁住的尺寸**重新撑开**。之前只在 `apply_text_size` 内部
   用 `_suppress_fit` 挡住，函数一返回、事件循环一转就被打回原形。
   → 之前那个「全部 PASS」的验证是**假阳性**：测试时 `user_data.json` 没数据，
   白框一直贴在最小高度 110，测不出撑开。

### 改法（布局契约重写）
`_fit_content_height(allow_grow=False)` 新规则：
- 白框高度 = `min(内容自然高度, 事件框长度设置, 窗口剩余可用高度)`
- 窗口高度**只收不放**：内容变少会跟着收，内容变多不再顶大窗口，多出的在框内滚动
- 唯一例外：启动后第一次排版（`self._allow_grow_once`）允许按内容撑到合适高度
- 新增 `_other_widgets_height()`：算布局里除白框外其它控件+间距+边距占的高度
- 新增 `self._fit_h`（基准窗口高度）：可用高度按它算，**不能按当前窗口高度算**——
  否则白框贪心填满 → sizeHint 恒等于当前高度 → 窗口被顶高后再也收不回来（踩过）
- `_fit_h` 只记「意图高度」`min(self.height(), target_h)`，避免把 Qt 强制顶高的
  几像素当成新基准
- `_programmatic_resize` 标志：区分「我们自己 resize」和「用户拖边框」，
  只有用户手动 resize 才更新 `_fit_h`
- `_resize_window()`：统一封装「setMinimumHeight(0) + resize」，Qt 不会自动回落窗口高度

### 字号 vs 图标：两者需求方向相反，故意做成两种行为
- **文字大小** → `_fit_content_height()`（不放开 grow）：窗口纹丝不动
- **图标大小** → `_fit_content_height(allow_grow=True)`：窗口跟着图标一起收/放
  （用户嫌图标占地方，调小图标就该整块变小，否则等于没省）
- 补偿时白框下限从 110 放宽到 60：宁可白框矮一点，也不把窗口顶大

### 实测（连跑 4 次，稳定）
- 字号 14→18→22→28→14：窗口恒定 (350,450)；白框 206→196→189→176→**206（完全还原）**
- 图标 48→80→100→150→200→100：窗口 302→334→354→404→454→**354（完全还原）**

### 测试踩坑
- 主窗口有每秒刷新的 QTimer，会在测量途中改内容 → 结果抖动（一度 3 次跑出 2 种结果）。
  **几何测试前必须 `for t in w.findChildren(QTimer): t.stop()`**
- 测试要灌入足量内容再测，否则白框贴着 110 下限，什么差异都测不出来
