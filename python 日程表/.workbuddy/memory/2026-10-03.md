# 2026-10-03 工作日志（日程表）

## 诊断报告到手 → 定位「透明度 0 存不住」的真凶

用户发来终端用户的诊断报告（`诊断报告_20261003_091709.txt`，Win7 SP1 64bit）。

### 报告给出的关键事实
- 配置文件存在、格式正常、可写、无 error.log
- 原文里明确写着 `"window_opacity": 0.0, "icon_opacity": 0.0`（**保存成功**）
- 报告第 4 节「程序启动时会读到的设置值」却显示 100%

→ 报告本身就把矛盾摆在眼前：**存进去了，读出来不对**。

### 真凶：`or` 吃掉了 0（只在值为 0 时发作的隐蔽 bug）
```python
self.window_opacity = float(self.user_settings.get('window_opacity') or 1.0)
```
Python 中 `0.0` 是 **falsy**，`or` 直接丢弃它返回 1.0。
所以**任何把透明度拉到 0 的用户，重启后必然被变回 100%**；
拉一半（0.5）正常 —— 这就是用户「怎么调都不对」的原因。

复现实测（修复前，同一份配置）：
- `启动后读到 window_opacity = 1.0`（文件里是 0.0）
- 白框 alpha=0.900、蓝条 alpha=0.800、图标 alpha=0.100 → 全是满值 = 白板

修复后实测：读到 0.0，白框/蓝条/图标 alpha 全部 0.000，文字仍 #333333 不透明。

### 修改
- 新增 `MyWindow._opacity_from(value, default=1.0)`：只有 `None` 才回落默认，
  脏数据/超范围/负数都有兜底，`0` 当合法值。
- 三处替换：主窗口 `__init__`、设置窗口读入（原写法会在关窗口时写回 1.0）。
- 顺手加固 `event_length`（同样 `or DEFAULT` 的 0 陷阱）+ 全项目扫了一遍
  `float(x.get(...) or 默认)` / `int(x.get(...) or 默认)` 写法。
- 新增 `verify_opacity_zero.py`：直接用诊断报告里的真实配置做回归。

### 顺带发现并修：开机自启动「假成功」
排查时 `verify_fixes` 的注册表断言失败，实测发现本机
**`SetValueEx` 返回成功但值读不回来**（杀软/沙箱静默丢弃写入）。
`set_autostart` 原来直接 `return True`，用户勾了会以为成功、开机啥也没有。
→ 改为写完**读回校验**（读不到/内容不符都返回失败并给出可操作提示）；
`verify_fixes` 也加了「写后读回」判定，把这类环境拦截标为 SKIPPED 而非 FAIL。

### 经验（值得记住的坑）
1. **`x or default` 不能用于「用户可设 0」的数值字段**。必须
   `default if x is None else x`。凡滑块类配置项都要警惕。
2. 配置文件诊断报告要**同时输出「文件原文」和「程序读到的值」**——
   两者不一致就是读取/应用环节的问题，比只看「文件在不在」强得多。
   本次正是靠这个矛盾一击定位。
3. 写外部状态（注册表/文件）后**必须读回验证**，不能信 API 返回值。
4. PySide2 反复 new/close 带定时器的 QMainWindow 会在退出时段错误
   （exit=139）；测试里模拟「重启」应复用实例、改配置后重跑读取逻辑。
5. 配置指向**本机不存在的文件**会让 `validate_and_load_data` 读 Excel
   时 access violation 崩溃 —— 造测试配置时 Excel 路径要指向真实文件。
6. 用 `python -u` 或重定向到文件跑验证脚本，否则管道里看不到输出、
   崩溃时还会丢现场；配 `-X faulthandler` 定位崩溃行很有效。
7. 长块字符串 Edit 匹配失败时，改用「行号定位 + 脚本精确改」更稳；
   注意中文锚点别打错字（这次把「开机自启动」写成「开机自动启动」导致定位失败）。
