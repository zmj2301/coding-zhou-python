一次分支切换引发的代码"集体消失"事故：取证、恢复与版本疑云

项目：Code Explorer（codingzhou.top） 时间：2026-10-01 版本：v2.6.8 收尾期间 关键词：Checkout-checkpoint、分支切换、工作区回退、线上恢复、证据链

一、事故是怎么被发现的

10-01 下午，按计划清理前一天的遗留待办：移除 worker.ts 里的调试日志、根治 build.py 双 index.html 问题。第一处编辑（worker.ts）顺利落盘，但从第二处开始，情况不对了——

  • build.py 的编辑工具报成功，磁盘上却是旧内容，mtime 变了、内容没变；
  • changelog 的新条目"写进去了"，重新读取却还是 2.6.6；
  • 更糟的是：根目录 index.html 从 419222 字节变成 413883，首页的层级浏览特征函数 enterPythonFolder 消失了。

连续多份文件集体"回到过去"，这不是单个编辑失败，是工作区被整体回退了。

二、取证：git 历史里的真相

盘点损害范围后查 git log，一条提交说明了一切：

55b6840 [Checkout-checkpoint] from win7-compat to main (16:38:44)

16:38 有一次 IDE 的分支切换检查点：从 win7-compat 分支切回 main 时，IDE 自动创建了一个 checkpoint 提交，把 main 上所有未提交的工作区改动直接覆盖掉了。v2.6.7 的全部未提交改动（首页层级浏览、python 页重写、changelog 条目）加上前一天写的文章，一夜清零。

这也解释了为什么编辑"报成功却不落盘"——编辑与回退发生了竞争，看到的磁盘状态已经是回退后的了。

三、恢复：线上站点就是备份

幸运的是，线上站点还保有全部最新版本（昨晚 21:32 部署的 bfb96717）。恢复思路很简单：部署产物写回源码。

  1. 从 https://codingzhou.top/、/python/、/changelog.json 下载三份线上文件；
  2. 检查 Worker 注入：逐处核对后发现，Worker 对首页的注入只发生在特定路由下的 window.__INITIAL_PROJECTS__ 赋值，静态资源本身是干净的，可以原样写回；
  3. 写回时逐一 grep 特征函数（enterPythonFolder、projects/tree）验证，changelog 首版本断言为 2.6.7——确认恢复的是最新版；
  4. 细节：changelog.json 保留原有的 BOM（utf-8-sig 习惯）；index.html 写回时 newline='' 防止换行符被改。

恢复完成后，再用 Python 脚本（绕开编辑工具落盘异常）重新应用 v2.6.8 的三处修改，每处改完立即验证落盘，然后走标准五步流程：changelog v2.6.8 → git commit（972e2e8）→ build → wrangler deploy（Version ID f9d03fdd）→ 清 KV 缓存。

结论：部署出去的版本就是一份天然备份——前提是它确实是最新版。

四、两个非交互环境的坑

  1. wrangler kv key delete 在 Windows 非交互环境下静默失败——退出码正常但 key 还在。最后改用 wrangler 的 OAuth 凭据直接走 Cloudflare REST API 逐个删除，成功。
  2. git-bash 的 curl 不解压 gzip——验证线上 HTML 时 curl -s | grep 匹配不到内容，误以为功能没上线。加 --compressed 或改用 Python urllib 才准确。这两个坑都差点把排查带进沟里。

五、版本疑云："你是不是上传错了版本？"

部署后用户质疑上线的可能是旧版。这个怀疑必须用证据回应，而不是嘴上保证。三方取证：

核对项 方法 结果
Cloudflare 部署历史 API 直查 昨晚 21:32（bfb96717）之后今天零部署，直到 16:58 的 f9d03fdd——不存在"今天早些时候有另一个版本在线上"
16:38 检查点快照 git show 55b6840 与线上部署逐一 diff 逐字节一致（唯一差异是 Cloudflare 自家的 __CF$cv$params 防机器人脚本）
项目列表 JSON 昨晚部署版 vs 现在版 63 个项目，零增减

结论：没有"更晚的版本"存在过，"今天早些时候的版本"和线上就是同一个。用户看到旧样子的真正原因是浏览器缓存——Ctrl+F5 强刷即可。另外 GitHub 的 origin/main 在 17:05 之前确实还是 9/27 的旧代码（v2.6.7 改动一直没推送成功），看仓库也会产生"旧版"错觉。

六、备份兜底

今早的分支状态（win7-compat，含检查点 55b6840）完整包含所有工作。推送 GitHub 做异地备份时网络极不稳定，放后台自动重试（每分钟一次），第 4 次成功：* [new branch] win7-compat -> win7-compat。至此 main 与 win7-compat 双分支、本地与 GitHub 双备份。

七、复盘：三条教训

  1. 未提交的工作区状态是最脆弱的。 一次分支切换就能全部抹掉。改完尽快 commit，多分支并行开发时尤其如此——这次事故的直接起因就是另一个会话在 win7-compat 上工作。
  2. 部署产物是天然备份，但要用特征函数验证。 恢复时不能只看文件大小（419222 vs 420160 只差注入），必须 grep 特征函数、断言版本号，确认"恢复的确实是最新版"。
  3. 质疑版本错乱时，用部署历史 + 快照 diff + 数据对比的三方证据链说话。 三份证据都指向同一结论时，才能安心说"没有版本可回滚"，并给出用户可自行验证的方案（带缓存穿透参数的 URL + 强刷指引）。
